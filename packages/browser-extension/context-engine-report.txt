SECTION 1 — CAPTURE PIPELINE
─────────────────────────────────────────────────────────────────────────────

ALL PLATFORMS share orchestration in src/content/shared.ts startSessionCapture().

CLAUDE (src/content/claude.ts)
Observer target: "main"
7 sequential strategies, each fallback if previous found no assistant:

S1: [data-testid="user-message"] (user), [data-testid="ai-turn"]/
    [data-testid="assistant-message"] (assistant). Outermost only.
S2: [data-testid="human-turn"]/[data-testid="ai-turn"] together.
    human-turn→user, ai-turn→assistant.
S3: [class*="font-claude-message"] → assistant only.
S5: h2.sr-only, h3.sr-only — if text starts "claude said"/"claude replied"/
    "assistant said"/matches /^claude[: ]/ → parent element is assistant turn.
S6: [data-test-render-count] as root anchor. Walks children, skips any
    containing [data-testid="user-message"]. Text > 20 chars → assistant.
S7: [data-testid="action-bar-retry"] (or action-bar-copy outside user-message).
    Walks UP from each bar until a sibling user-message is found. That ancestor
    container IS the assistant turn.
S4: Structural — walks up from first user element up to 15 levels, finds first
    ancestor with >= userCount children where at least one child is NOT a
    user-message. All non-user children of that container → assistant.

Code blocks: extractMessageContent() in shared.ts line 236:
  Clones element → converts each <pre><code> to "\n```lang\ncode\n```\n" text node
  (language from codeEl.className /language-([\w-]+)/) → strips CF_CHROME_SELECTORS
  (button, svg, role=button/toolbar, *copy/*action/*retry/*thumbs/*feedback,
  *tooltip — NOTE: role="group" explicitly kept because Claude uses it for content)
  → getTextContent() tree-walker (no layout needed) → collapse 3+ newlines.

Weaknesses:
  - All timestamps assigned Date.now() at scrape time, not from DOM.
    Multiple messages in same millisecond → chunk ID collision in attention engine
    (id = "${sessionId}-msg-${timestamp}-${role}").
  - S5 depends on accessible heading text content — breaks in non-English UI.
  - S6 depends on data-test-render-count existing.
  - If all 7 strategies fail simultaneously → empty capture.

GROK (src/content/grok.ts)
Observer target: "main"
4 strategies:
A: [class*="UserMessage"]/[class*="AssistantMessage"], class→role.
B: [data-message-author-role] (ChatGPT-compatible).
C: Class substrings — user-message/user-query/user-bubble/query-bubble (user);
   bot-message/assistant-message/response-bubble/model-response (assistant).
D [DANGEROUS FALLBACK]: [class*="message"]/bubble/turn/chat-item.
   Role assigned by index: i % 2 === 0 → "user", odd → "assistant".
   This alternating heuristic is WRONG if conversation has welcome messages,
   system messages, or consecutive same-role messages. Produces corrupted
   role assignments for all subsequent messages.

SECTION 4 — ATTENTION ENGINE (TIER 3)
─────────────────────────────────────────────────────────────────────────────

File: src/lib/attention-engine.ts (1079 lines, singleton export `attentionEngine`)

MODEL LOADED:
  Both balanced and full tiers: Xenova/all-MiniLM-L6-v2 (384-dim, ONNX).
  No gte-tiny model exists in codebase. DEFAULT_MODEL_ID = "Xenova/all-MiniLM-L6-v2".
  Minimal tier: no model. Pure keyword scoring.
  Model cached in browser cache after first download (~23MB).

HARDWARE TIER DETECTION (src/lib/capability-detector.ts):
  Signals: navigator.hardwareConcurrency, navigator.deviceMemory,
  performance.memory.jsHeapSizeLimit, WebGPU requestAdapter(), WebGL renderer,
  getBattery(), 5ms CPU benchmark (ops/ms).
  MINIMAL: cores < 2, bench < 300 ops/ms, RAM < 4GB, heap < 1024MB.
  FULL: WebGPU + (bench >= 1200 OR cores >= 6) + (RAM >= 8GB OR heap >= 3072MB).
  BALANCED: everything else.
  Battery: on-battery → downgrade one tier (unless user forced "full").
  Override: localStorage["contextforge:tier-override"] or chrome.storage.local["cf_tier_override"].
  Cache TTL: 30 minutes. Re-evaluates battery+override on each call.
  Load watchdog (monitorLoad): setInterval every 250ms. If event loop stalls
  > 1000ms between samples, emits downgrade event. AttentionEngine.downgradeToMinimal()
  drops the model; subsequent embeds return zero-vectors → keyword fallback.

TIER CONFIGS:
  minimal:  useEmbeddings=false, no model, no tree-sitter, targetMs=100
  balanced: wasm, 2 threads, batchSize=16, maxChunks=500, useTreeSitter=true, targetMs=2000
  full:     webgpu, 4 threads, batchSize=32, maxChunks=2000, useTreeSitter=true, targetMs=5000

EMBEDDING GENERATION:
  loadEmbeddingModel() (line 515):
    SharedArrayBuffer check → multi-threading: threads = min(maxWasmThreads, hardwareConcurrency).
    If no SAB: 1 thread only.
    WebGPU: full tier requests adapter; if no adapter → falls back to wasm.
    pipeline("feature-extraction", modelId, {device?, progress_callback}).
    Failure → modelAvailable=false → keyword fallback.
  
  getEmbedding(text) (line 870):
    extractor(text, {pooling: "mean", normalize: true}).
    Returns Float32Array[384] as number[].
    Failure → Array(384).fill(0) → keyword fallback.
  
  embedChunks(chunks) (line 883):
    Processes in batches of batchSize (16 or 32).
    CRITICAL LINE 895: texts = batch.map(c => c.content.slice(0, 512))
    Content TRUNCATED TO 512 CHARS before embedding.
    MiniLM-L6 has 512-TOKEN context (~1500-2000 chars), so this truncates
    even moderately long messages before the model limit is reached.
    A 3000-char assistant explanation has its second half completely ignored
    for semantic similarity purposes.

COSINE SIMILARITY (line 846):
  Standard: dot / (|a| * |b|). Returns 0 if dimensions mismatch or both zero.
  If task embedding is all-zeros (model failed) → keywordScore() used instead.

KEYWORD FALLBACK (line 860):
  Tokens: query.toLowerCase().split(/\W+/).filter(w => w.length > 2).
  Score: hits (exact substring matches) / total tokens.
  No IDF weighting. No stemming. No synonym expansion.

AST CHUNKING / TREE-SITTER:
  Implemented: initTreeSitter() loads web-tree-sitter runtime + grammar WASMs.
  Grammar files: tree-sitter-typescript.wasm, tsx, javascript, python, rust, go.
  Location: chrome.runtime.getURL("grammars/...") in extension context.
  6-second timeout per grammar file (Promise.race with setTimeout reject).
  Fallback: parseWithRegex() for all 6 languages.
  parseWithTreeSitter() extracts: functions, classes, imports, exports, dependencies.
  parseWithRegex() uses matchAll patterns for each language.
  Results stored in AppStructure.files[] in IDB, merged (not overwritten).

VECTOR CACHING:
  Implemented via "contextforge-attention" IndexedDB.
  3 stores: ae_chunks (keyPath="id", index "sessionId"), ae_structure,
  ae_sessions_meta (keyPath="sessionId").
  indexSession() checks meta.messageCount === session.messages.length.
  If match → skip. If session grew → RE-INDEX ALL CHUNKS FROM SCRATCH.
  Delta-only indexing is NOT implemented.

RANKING AND SELECTION (buildAttentionMap, line 357):
  1. Embed task query string.
  2. Load all chunks for session from IDB.
  3. Score each: cosine similarity OR keyword score.
  4. Sort descending by score.
  5. CRITICAL: scored.slice(0, SEARCH_TOP_K).filter(c => c.relevanceScore >= threshold)
     SEARCH_TOP_K = 30. Slices to top 30 FIRST, then applies threshold.
     If threshold=0.7 (strict) and only 3 of top 30 exceed it → only 3 chunks pass.
     A session with 500 chunks where chunk #31 has score 0.8 — that chunk is
     NEVER considered because it was cut by SEARCH_TOP_K before threshold filtering.
  6. Last TAIL_SIZE (6) messages always added with relevanceScore=1.0.
  7. Merged = topChunks + tail (deduped by chunk id).

summarizeWithAttention() (summarizer.ts line 572):
  Runs attentionEngine.buildAttentionMap() to get topChunks.
  For each message: if idx >= tailStart → verbatim.
  If score >= threshold → stripLowScoreCode (keep high-score code, remove low-score).
  If score < threshold → first sentence ≤200 chars, all code removed.
  Builds ExtractedContext from processed messages. Returns buildPlainTextSummary().

AbortController: NOT implemented. No way to cancel an in-flight indexSession().

SECTION 5 — QUALITY LOSS AUDIT
─────────────────────────────────────────────────────────────────────────────

FULL CONTEXT:
  Code blocks surviving: YES for < 30 msgs. For > 30 msgs, oldest 30+ are dropped
  (extractAllCodeBlocks reverses to process newest first, stops at MAX_CODE_BLOCKS=30).
  Message order: YES, preserved by DOM compareDocumentPosition sort.
  Role accuracy: Claude (7 strategies, generally reliable), ChatGPT (reliable),
  Gemini (reliable), Grok (Strategy D BROKEN — alternating index),
  DeepSeek (heuristic fallback can misclassify), Perplexity (Strategy D user-less).
  Token limit: 30k char cap drops unknown middle section silently.

SMART SUMMARY:
  Key decisions captured: only if matching 6 TIER2_DECISION_RE patterns.
  Patterns like "going with X", "opted for", "let's use" not covered → MISS.
  Code summarized when shouldn't be: NO — code blocks extracted verbatim always.
  goal.current accuracy: last 6 USER messages only. If last assistant message
  introduced a new direction not yet reflected in user follow-up → goal.current
  is stale. Misrepresents "current focus" in translator output.
  Old important messages dropped: YES. Any decision/bug sentence from early
  messages IS captured if it matches patterns. But user context from middle
  messages (not first, not last 6) is completely absent.
  Completed/pending: NOT EXTRACTED in Tier 2 at all.

ATTENTION ENGINE:
  Embeddings capturing semantic meaning: YES for content ≤512 chars.
  For longer messages: only first 512 chars influence the embedding.
  A 2000-char message discussing problem+solution+code → only problem portion
  embedded. If task query matches "solution" terminology in the second half,
  that message may score LOW and be compressed to 1 sentence.
  
  Similarity threshold aggressiveness: YES, too aggressive in practice.
  strict=0.7 with SEARCH_TOP_K=30 can result in very few chunks (3-5) surviving
  before the mandatory 6-message tail is added. Entire session context → 9 messages.
  light=0.4 is more reasonable but still limited by the top-30 pre-filter.
  
  Code blocks scoring: Code chunks embedded separately from message chunks
  (sessionToChunks() creates both). Code content also truncated to 512 chars
  at line 895. Long file contents have truncated embeddings.
  
  Ranking missing context: YES, due to SEARCH_TOP_K=30 pre-filter (see above).
  
  After optimization changes: quality can drop if session has > 30 relevant chunks
  because the top-K cutoff prevents any chunk beyond rank 30 from even being
  considered against the threshold.

DID ANY OPTIMIZATION REDUCE CONTEXT QUALITY?
YES. The 512-char truncation at attention-engine.ts line 895 is the most
impactful quality-reducing implementation choice. MiniLM-L6 has a 512-TOKEN
context window (~1500-2000 chars). Truncating input at 512 CHARS means only
~128 tokens are used — the model runs at ~25% of its designed capacity.
This makes the embeddings less accurate for any message longer than a single
short paragraph, which includes most assistant responses with explanations.
This was likely added to "optimize" throughput but reduces recall quality.

─────────────────────────────────────────────────────────────────────────────
SECTION 7 — ROOT CAUSE OF QUALITY LOSS
(ranked by severity)
─────────────────────────────────────────────────────────────────────────────

1. attention-engine.ts line 895 — 512-char truncation before embedding
   What is lost: semantic meaning of second half of any message > 512 chars.
   Why: embedChunks() calls c.content.slice(0, 512) on every chunk.
   Severity: HIGH — affects all attention engine migrations on any non-trivial
   session. Any assistant message with explanation + code gets embedding based
   only on first ~128 tokens.

2. attention-engine.ts line 393 — SEARCH_TOP_K applied before threshold filter
   What is lost: relevant chunks ranked > position 30 never evaluated.
   Why: scored.slice(0, SEARCH_TOP_K).filter(>= threshold) cuts before filtering.
   Chunk #31 with score 0.9 is discarded before the threshold check.
   Severity: HIGH — for sessions > 30 messages, genuinely relevant context
   is excluded regardless of how semantically relevant it is.

3. grok.ts lines 62–73 — Strategy D alternating role assignment
   What is lost: correct role identity for all messages in Grok sessions that
   fall through to Strategy D.
   Why: i % 2 === 0 assigns "user"/"assistant" by position, not content.
   Severity: HIGH — entire session context has wrong speaker labels.
   All downstream extractors (goal from user msgs, decisions from assistant msgs)
   operate on corrupted data.

4. service-worker.ts lines 736–750 — 30k char hard cap drops middle silently
   What is lost: middle section of any session whose formatted prompt exceeds
   30,000 chars. No notification to user about what was dropped.
   Why: ProseMirror/Lexical freeze on large pastes; 30k is practical chat limit.
   Severity: HIGH — long sessions (100+ messages) almost certainly hit this cap
   after adding code blocks and structure.

5. summarizer.ts line 294–299 — DECISION_RE misses common decision patterns
   What is lost: decisions phrased as "going with X", "opted for", "let's use",
   "I'll stick with", "switching to", "using X because" are not captured.
   Why: only 3 regex patterns cover decision sentences (Tier 1).
   Severity: MEDIUM — quantitatively significant for engineering conversations.

6. summarizer.ts line 324 — extractFacts() only scans first 20 messages
   What is lost: technical constraints, API keys, version numbers, config values
   stated after message position 20.
   Why: earlyMessages = messages.slice(0, Math.min(20, messages.length)).
   Severity: MEDIUM — a session where constraints were introduced after early
   context-setting exchanges misses those facts entirely.

7. summarizer.ts line 341 — MAX_CODE_BLOCKS = 30, newest-first
   What is lost: all code blocks from the first part of the session if > 30 blocks.
   Why: extractAllCodeBlocks() reverses messages, processes newest first, stops at 30.
   Severity: MEDIUM — early architectural scaffolding code dropped in favor of
   latest edits, losing original structure context.

8. summarizeIntelligent() — no completed/pending extraction
   What is lost: task completion state — what was done, what remains.
   Why: IntelligentSummary interface has decisions/bugsFixed but no
   completed/pending. These fields were not ported from extractContext().
   Severity: MEDIUM — migrated context has no task checklist, requiring user
   to reconstruct progress manually.

9. summarizer.ts line 238–247 — extractCurrentFocus() uses last 3 USER messages
   What is lost: if last several messages were assistant-only (long explanation
   followed by user saying "ok" or nothing yet), currentFocus is stale.
   Why: filters messages to user role only before taking last 3.
   Severity: LOW-MEDIUM — accurate most of the time but fails at conversation
   boundaries where assistant drove the last exchange.

10. attention-engine.ts sessionToChunks() — chunk IDs collision risk
    What is lost: if two messages share same timestamp (same scrape call), their
    chunk IDs are identical: "${sessionId}-msg-${timestamp}-${role}".
    Second write overwrites first in IDB.
    Why: timestamps from Date.now() at scrape time, not per-message.
    Severity: LOW — rare in practice but silent data loss.

SECTION 8 — RECOMMENDED FIXES
─────────────────────────────────────────────────────────────────────────────

FIX 1 — 512-char truncation (HIGHEST IMPACT)
  Change: attention-engine.ts line 895
  From: const texts = batch.map(c => c.content.slice(0, 512))
  To:   const texts = batch.map(c => c.content.slice(0, 2000))
  Why: MiniLM-L6 handles ~512 tokens (~1500-2000 chars). Current 512-char limit
  uses only ~25% of model capacity. 2000 chars = ~500 tokens = 97% capacity.
  Effort: Quick (1 line). Risk: slight slowdown per batch due to longer sequences.

FIX 2 — SEARCH_TOP_K filter order
  Change: attention-engine.ts line 393
  From: scored.slice(0, SEARCH_TOP_K).filter(c => c.relevanceScore >= threshold)
  To:   scored.filter(c => c.relevanceScore >= threshold).slice(0, SEARCH_TOP_K)
  Or:   increase SEARCH_TOP_K from 30 to 100.
  Why: Threshold should filter semantically, not be gated by arbitrary rank cutoff.
  A relevant chunk at rank 50 scores higher than an irrelevant one at rank 5.
  Effort: Quick (1 line). May include more context — positive for quality.

FIX 3 — Grok Strategy D role assignment
  Change: grok.ts lines 62–73
  Remove Strategy D entirely, or replace with content analysis:
    if (el.querySelector('pre, code, [class*="markdown"]')) → "assistant"
    else if ((el.textContent?.length ?? 0) > 50) → use structural heuristic
  Why: Alternating by index is provably wrong for any non-strictly-alternating
  conversation layout.
  Effort: Quick.

FIX 4 — DECISION_RE coverage
  Change: summarizer.ts DECISION_RE array (line 295)
  Add patterns:
    /\bgoing with\b/im
    /\bopted for\b/im
    /\blet['']s use\b/im
    /\bsticking with\b/im
    /\bswitching to\b/im
    /\binstead I['']ll\b/im
  Why: Current patterns miss the most common English phrasings for decisions.
  Effort: Quick.

FIX 5 — extractFacts() scan limit
  Change: summarizer.ts line 324
  From: const earlyMessages = messages.slice(0, Math.min(20, messages.length))
  To:   scan ALL messages for FACT_RE (keep cap of 8 results)
  Why: Technical constraints are often introduced mid-conversation.
  Effort: Quick.

FIX 6 — Add completed/pending to summarizeIntelligent()
  Change: summarizer.ts — add completed/pending extraction to summarizeIntelligent()
  using same COMPLETED_RE/PENDING_RE patterns from extractContext().
  Add completed and pending fields to IntelligentSummary interface.
  Update buildClaudePromptTier2/buildMarkdownPromptTier2 to render them.
  Why: Tier 2 migrations completely lack task state information.
